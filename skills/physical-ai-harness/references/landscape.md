# Physical AI Harness Landscape — verified snapshot
**Verified: 2026-10-12.** Entries were confirmed against live sources on this date — re-verify anything before relying on it if this snapshot is more than ~6 months old.

## Position and framing
- **Harness Engineering for Physical AI: Robot Middleware Is the Harness Layer** — position paper by Sanghoon Lee, Jiyeong Chae and Kyung-Joon Park (arXiv:2606.09416, cs.RO, submitted 2026-06-08). It argues that robot middleware is the "harness" for learned policies, planners and VLA models, and names three functions middleware lacks for AI models: Projection (check each output as it is emitted), Isolation (bound the model's execution and transmission slot) and Transfer (fall back to a verified baseline when checks fail). It sketches a "ROS 2 Harness Profile" that declares a model's output region, inference budget and operating regime for enforcement across ROS 2, DDS and Zenoh. The bibliography (opened in the HTML version) cites Alshiekh 2018 (shielding), Ames 2019 (control barrier functions), Sha 2001 and Phan 2020 (Simplex, Neural Simplex), Corsaro 2023 (Zenoh) and Qin 2026 (below); it does not cite ros2_control, asynchronous inference or real-time chunking, so those parts of this snapshot are the skill's own mapping, not the paper's. Status: research (preprint). Source: https://arxiv.org/abs/2606.09416 — Source: https://arxiv.org/html/2606.09416
- **Harnessing Embodied Agents: Runtime Governance for Policy-Constrained Execution** — the governance framework the harness paper cites as an external layer between application and ROS 2. Qin, Luan, See, Boukhers, Yang and Li (arXiv:2604.07833, first submitted 2026-04-09, v4 revised 2026-06-10) move safety and recovery out of the agent loop into a runtime layer that does policy checking, capability admission, execution monitoring, rollback and human override. They report, in over 1,000 randomized simulated trials, about 96% interception of unauthorized actions and about 91% recovery success; these are simulation numbers from the authors. The harness paper notes this framework does not reach end-to-end models that emit continuous actions. Status: research (preprint). Source: https://arxiv.org/abs/2604.07833

## Runtime assurance building blocks
- **Neural Simplex Architecture** — runtime assurance for neural controllers built on the Simplex architecture of Sha et al. Plain Simplex hands control to a baseline controller and usually keeps it there; Neural Simplex adds switching control back to the advanced controller and online retraining. Case studies: a target-seeking ground rover navigating an obstacle field and a neural controller for an artificial pancreas. Phan, Grosu, Jansen, Paoletti, Smolka and Stoller; arXiv:1908.00528, v1 2019-08-01, v2 2020-03-24 (the arXiv comments field lists NFM 2020). The harness paper's bibliography cites it (Phan 2020). Status: research. Source: https://arxiv.org/abs/1908.00528
- **Control Barrier Functions: Theory and Applications** — overview of control barrier functions, used to verify and enforce safety in optimization-based safety-critical controllers, with applications including robotic systems. Ames, Coogan, Egerstedt, Notomista, Sreenath and Tabuada; arXiv:1903.11199 (2019-03-27). Status: research (survey). Source: https://arxiv.org/abs/1903.11199
- **Safe Reinforcement Learning via Shielding** — synthesizes a reactive "shield" from a temporal-logic specification. The shield either lists safe actions before each decision or monitors the learner's chosen action and corrects it only when it would violate the specification; the paper also discusses what a shield must satisfy to preserve the learner's convergence guarantees. Alshiekh, Bloem, Ehlers, Könighofer, Niekum and Topcu; arXiv:1708.08611 (2017-08-29). Status: research. Source: https://arxiv.org/abs/1708.08611

## ROS 2 enforcement surfaces
- **ROS 2 managed (lifecycle) node design** — primary states `Unconfigured`, `Inactive`, `Active` and `Finalized`; supervisory transitions `create`, `configure`, `cleanup`, `activate`, `deactivate`, `shutdown`, `destroy`. An `Inactive` node "will not receive any execution time to read topics" and service requests to it fail immediately, so deactivating a node stops it reading topics. Status: ROS 2 core design document. Source: https://design.ros2.org/articles/node_lifecycle.html
- **ROS 2 QoS deadline, liveliness and lifespan** — design article for three policies a harness can use as timing guards. Deadline is the maximum gap between messages (0 disables it); lifespan is how long a message stays valid (0 disables it) and expired messages are not delivered; liveliness has levels `LIVELINESS_AUTOMATIC` and `LIVELINESS_MANUAL_BY_TOPIC`, plus a system default. Status changes reach the application through optional event callbacks passed when creating publishers and subscribers (the design calls them "Resource Status Events"), which fire when the executor checks. The article words this as a proposal ("would be"). Status: ROS 2 core design document; the page does not name the user-facing callback types. Source: https://design.ros2.org/articles/qos_deadline_liveliness_lifespan.html
- **Fast DDS standard QoS policies** — eProsima's API reference lists `DeadlineQosPolicy`, `LifespanQosPolicy`, `LivelinessQosPolicy` and `LivelinessQosPolicyKind` in its C++ and Python API reference sections, so the DDS-level versions of the guards above exist in this vendor. The page index confirms only the names; entity applicability and semantics were not read here. Status: maintained vendor documentation (not verified further). Source: https://fast-dds.docs.eprosima.com/en/latest/fastdds/dds_layer/core/policy/standardQosPolicies.html
- **rcl_interfaces ParameterDescriptor** — the parameter metadata message. `floating_point_range` and `integer_range` each hold a from-value, a to-value and a step, are mutually exclusive, and apply a range constraint; `read_only` (default false) when true means the value cannot change after initialization. Status: ROS 2 core interface (rolling branch). Source: https://raw.githubusercontent.com/ros2/rcl_interfaces/rolling/rcl_interfaces/msg/ParameterDescriptor.msg
- **ros2_controllers JointTrajectoryController** — the controller parameter page lists `cmd_timeout` (double, default 0.0; "Timeout after which the input command is considered stale", counted from the end of the trajectory, "must be greater than `constraints.goal_time`, otherwise ignored", zero deactivates it), `constraints.goal_time` (default 10.0) and `constraints.stopped_velocity_tolerance` (default 0.01). The user guide says that when tolerances are violated during trajectory execution the action goal is aborted, the client is notified and the current position is held. The parameter page lists no parameter that enforces joint limits (the only "limit"-like ones are the `u_clamp` and `i_clamp` gains). Status: maintained (rolling documentation). Source: https://control.ros.org/rolling/doc/ros2_controllers/joint_trajectory_controller/doc/parameters.html — Source: https://control.ros.org/rolling/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html
- **ros2_control soft joint limits** — the `joint_limits` API stores soft limits from the URDF `<safety_controller>` tag (`soft_lower_limit` and `soft_upper_limit`, both optional with default 0, plus `k_position` optional and `k_velocity` required). The jazzy API page lists the struct `SoftJointLimits` with members `min_position`, `max_position`, `k_position` and `k_velocity`. Status: maintained (API documentation). Source: https://control.ros.org/jazzy/doc/api/structjoint__limits_1_1SoftJointLimits.html
- **rmw_zenoh and Eclipse Zenoh** — rmw_zenoh is the ROS 2 RMW using Zenoh as the middleware, built on zenoh-cpp. Its README says multicast discovery is disabled by default in the node's session config, so nodes get peer information through the Zenoh router (started with `ros2 run rmw_zenoh_cpp rmw_zenohd`); it also shows `ZENOH_CONFIG_OVERRIDE='scouting/multicast/enabled=true'` for router-less discovery between same-host nodes. It gives `sudo apt install ros-<DISTRO>-rmw-zenoh-cpp` for binaries. Zenoh itself is described as "Zero Overhead Pub/Sub, Store/Query and Compute", with the Rust `zenoh` crate as the reference implementation and libraries for C, C++, Python, Kotlin, Java, TypeScript and Go (not all are direct Rust bindings; the TypeScript one is a WebSocket client). Status: ROS 2 RMW repository in the ros2 GitHub org; Zenoh repository in the eclipse-zenoh org. Source: https://github.com/ros2/rmw_zenoh — Source: https://github.com/eclipse-zenoh/zenoh
- **QoS Guard (Dependency Chain Analysis of ROS 2 DDS QoS Policies)** — Lee, Kang and Park (arXiv:2509.03381, 2025-09-03) model dependencies among 16 DDS QoS policies across discovery, data exchange and disassociation, define 41 dependency violation rules, and ship QoS Guard, a ROS 2 package that checks DDS XML profiles offline before deployment. Useful for checking that a harness's deadline and liveliness settings are consistent before the robot runs. Status: research with a released package. Source: https://arxiv.org/abs/2509.03381

## Monitoring and runtime verification
- **ROSMonitoring (and ROSMonitoring 2.0)** — formalism-agnostic runtime verification for ROS. Monitors are generated from a YAML configuration and can run non-intercepting (observe a topic) or intercepting (publisher-side or subscriber-side, via `<topic>_mon`), and offline (log only) or online (with an oracle speaking JSON over WebSocket). The README lists ROS 1 and ROS 2 topic and service monitoring, with ROS 2 monitors generated as an `ament_python` package; the 2.0 paper (Saadat, Ferrando, Dennis and Fisher, arXiv:2411.14367, 2024-11-21) adds services and message ordering and states ROS 1 plus partial ROS 2 support. Intercepting monitors publish or subscribe through `<topic>_mon`. Status: research tool; README shows 3 commits and no visible last-activity date. Source: https://github.com/autonomy-and-verification-uol/ROSMonitoring — Source: https://arxiv.org/abs/2411.14367

## Policy deployment timing
- **Real-Time Chunking (Real-Time Execution of Action Chunking Flow Policies)** — Black, Galliker and Levine (arXiv:2506.07339, v1 2025-06-09, v2 2025-12-05, NeurIPS 2025). An inference-time method that lets diffusion- or flow-based action-chunking policies run asynchronously without retraining: the next chunk is generated while the current one executes, with already-committed actions held fixed and the rest inpainted. Tested on 12 dynamic tasks in the Kinetix simulator and 6 real bimanual tasks. The follow-up by Black, Ren, Equi and Levine (arXiv:2512.05964, 2025-12-05) moves the conditioning on committed action prefixes into training to remove the inference-time inpainting cost. Status: research. Source: https://arxiv.org/abs/2506.07339 — Source: https://arxiv.org/abs/2512.05964
- **LeRobot asynchronous inference** — decouples action prediction from execution with a `PolicyServer` and a `RobotClient` that can run on separate machines, so the next action chunk is computed before the current one is exhausted. Key parameters are `actions_per_chunk` (more actions lower the chance of an empty queue but can make actions less precise) and `chunk_size_threshold` (values near 0.0 collapse to synchronous behavior), with `aggregate_fn_name` for overlapping chunks. The guide advises lowering `fps` if the client keeps running out of queued actions. The page shows 0.7 as the table default and 0.5 in its example command, so check the installed version. Status: maintained (Hugging Face LeRobot documentation). Source: https://huggingface.co/docs/lerobot/async
