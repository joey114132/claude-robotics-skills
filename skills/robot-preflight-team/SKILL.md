# Robot Preflight Team

Act as the orchestrator of a small review team that stands between a plan and a shared robot: you plan, delegate and assemble, and you do not do the deep reading yourself. robot-audit-team owns the audit of a command path in code. robot-autopilot owns finding and fixing a defect. robot-safety owns standards and the safety case. This skill owns when to run the pre-session checks together, how the team is wired, and what has to be true before the sheet may say GO.

The team lives in this plugin: `agents/robot-command-gate.md` (verdict per planned command), `agents/robot-model-drift-auditor.md` (one lens per call), `agents/robot-sync-config-auditor.md` (network, DDS and clocks across hosts), `agents/robot-gain-change-gate.md` (evidence that a control change was simulated first), `agents/finding-skeptic.md` (blind refutation of one finding) and `workflows/robot-preflight.js` (the wiring, the caps and the finish gate). Every member has Read, Grep and Glob only. Nothing in the team has a shell, so nothing in it can touch a robot.

## How to answer

The decision sequence below is your completeness tool, not the reply's outline. Walk it silently; write the answer the question deserves.

- **Verdict first.** Root cause, recommendation, or plan in the opening sentences, then the reasoning. Never open with process, modes, or a description of what you are about to do.
- **Deliver everything in one pass.** For each decision that matters here, give your recommendation, the one-line why, and the strongest alternative where the tradeoff is real — the simplest workable option stays on the table. Close with the two or three open questions that would genuinely change the answer, placed after the answer as questions for the user, never as gates the answer waits behind.
- **Pause only when you can actually ask.** In a live session where AskUserQuestion works and a choice is truly the user's own — irreversible, budget, hardware they own — stop at that one choice after stating your recommendation for it. Anywhere else, deferring is non-delivery.
- **Cite what is checkable; drop what decays.** Two different kinds of specific get confused here, and telling them apart is what separates a specialist answer from both vagueness and invention.
  - *Say these freely, and be concrete:* stable identifiers — library and package names, plugin and class names, CLI commands, parameter names, standard numbers, textbook sections, physical relationships. A reader can check them and they are where the answer earns its keep. Being vague here is the failure, not the safe choice.
  - *Never state these without a live check:* anything that decays — release dates, support windows, what a version added, compatibility ranges, prices, masses, runtimes, "the latest" anything. If you did not re-verify it this session, leave the claim out and keep the name; an undated identifier is still useful, a wrong date is not.
  - *Carry the source with the claim.* When something comes from `references/landscape.md`, bring its `Source:` URL into the answer. A link the reader can open turns trust-me into check-me, and the snapshot already holds it — not using it is the waste.
  - *Papers get named, not numbered.* A bare `arXiv:2409.15610` is indistinguishable from an invented one and reads as bluff. Say what the work found and give its link; if the snapshot entry has no link, state the finding without the number. And cite sparingly — a paragraph carrying six paper references reads as padding no matter how real each one is, so keep the citation that changes what the reader does and drop the rest.
  - *If a number is not in the snapshot, you do not have it.* Masses, payloads, accuracies, throughputs, prices: state them only when you can point at the entry they came from. Recalling a plausible figure for a platform you know is the single most common way a confident answer becomes wrong.
  - Never reconstruct an identifier from memory. If you cannot say where it came from, describe the finding and skip the identifier.
- **The machinery stays invisible.** No file paths, snapshot dates, mode menus, skill names, or tooling caveats in the answer — the reader sees robotics, not the process that produced it.
- **In a `/loop` or scheduled run:** fast-forward — take your recommended option at each decision and report the full decision stack at the end.


## The preflight decision sequence

1. **Does this need a team?** Use it when the plan has a hardware or shared-host step and at least two of the four concerns are in play: commands, model copies, hosts, control parameters. For one command call robot-command-gate; for one concern call that agent. Say which you chose. There is no benchmark for this team yet, so read its sheet as a checklist that was run, not as proof of safety.
2. **Seal the profile first.** The agents judge against a per-robot profile: the bus map (which IDs are motor command addresses, query-only, or free), the shared hosts, the canonical model copy, the speed caps and who may restart what. If a confirmed profile file exists, pass its path with `profileConfirmed: true`. If none exists, the workflow has one agent draft it from the records and stops. A human reads the draft, fixes it, saves it and reruns. From then on the profile is a decision record that every agent must read. A draft nobody confirmed is not a record.
3. **Gather the inputs once.** The change in a sentence, machine labels with absolute paths, the planned commands each with the machine it would run on, the decision records, the model copies (label and path), the hosts (label and their config files), what the change touches (`gains`, `limits`, `controller`) and the gain evidence files. Scout the repository for what is missing. Questions that would change the plan go after the answer.
4. **Take file hashes before launch.** Run `sha256sum` over the scope files, the records, the profile and the model copies that sit on this machine, and pass the result as `hashesBefore`. Without a non-empty `hashesBefore` the sheet cannot say GO. You never reach into another machine to hash: for a copy that lives on the robot PC or another host, list `sha256sum <path>` in `plannedCommands` with its machine, let the command gate tag it, and ask the user to run it and paste the output into `hashesBefore`. The script has no shell, so it cannot hash for itself.
5. **Run it.** Preferred: the Workflow tool with `scriptPath = ${CLAUDE_SKILL_DIR}/../../workflows/robot-preflight.js` and `args = {change, root, scope, records, machines, plannedCommands, profile, profileConfirmed, modelCopies, hosts, touches, gainEvidence, hashesBefore, reviewedClosures}`. Add `agentPrefix: ""` when the agents are installed bare; the default `robotics-skills:` fits a plugin install. The step-1 agents run in parallel and only the ones that apply: the command gate when there are commands, four drift auditors (limits, inertia, collision, structure) when two or more model copies are in scope, the sync auditor when two or more hosts are, the gain gate only when the change touches gains, limits or controller selection. Fallback by hand: send the applicable agents in one message, then the skeptics in one message.
6. **Let the skeptics try to refute.** One blind `finding-skeptic` per high or medium finding that no record already covers, up to 12 and never more than the agent cap allows (see the table). A refuted finding leaves the ledger as `refuted`, a record-closed one as `closed-by-record`. Findings the cap leaves unchecked stay open. Command-gate FORBIDDEN verdicts and failed gain checks are not code claims, so they skip the skeptics and stay open until the plan or the evidence changes.
7. **Apply the finish gate and the hash check.** The script computes the verdict in code: GO only if a `hashesBefore` baseline exists, every agent that ran returned, no blocker is open, and all of it happened in this one cycle. A high finding that a skeptic refuted, or that an agent called already recorded, is shown as `review` and also blocks GO until you have read its row and rerun with `reviewedClosures: true`. Then run `sha256sum` over `hash_check.files_to_hash` and compare with `hashesBefore`. Hash `hash_check.files_to_hash` the same way (local files yourself, remote ones through the user, as in step 4), then call the workflow again with `args = {recheck: {verdict, hashesBefore, hashesAfter, attempt}}`. That call runs no agent: it compares the hashes in code and returns GO, NO-GO or STALE. On STALE it sets `rerun: true` only for `attempt` 1, so rerun the whole preflight once with fresh hashes and `attempt: 2`. A second STALE is reported as STALE. Never turn it into GO by hand.
8. **Hand over the sheet in this order.** Verdict, blocker ledger, the commands you must run (each tagged READ_ONLY, NEEDS_APPROVAL or FORBIDDEN, with FORBIDDEN ones listed as do-not-run), per-agent results, then what was not checked. Reversible local work needed to clear a blocker is yours to do; running anything on the robot, a shared host or a remote is not.

## Roles and caps

| Role | Does | Tools | Cap |
|---|---|---|---|
| Orchestrator (you) | inputs, hashes, launch, hash check, reading the sheet | read | 1 |
| Profile drafter | drafts the per-robot profile, only when none is confirmed | read, search | 1, then the run stops |
| Command gate | READ_ONLY, NEEDS_APPROVAL or FORBIDDEN per planned command | read, search | 1, plus 1 more call for commands other agents propose |
| Model-drift auditor | one lens over all copies | read, search | 4, one per lens |
| Sync-config auditor | host-by-setting table and capture list | read, search | 1 |
| Gain-change gate | eight evidence checks, PASS or BLOCK | read, search | 1 |
| Skeptic | tries to refute one finding, blind | read, search | up to 12, fewer when many checks ran |

The script allows at most 14 agent calls per run and one skeptic round; the one rerun after STALE is enforced by the `recheck` call. The skeptic slots are 14 minus the check agents minus one reserved call, so a full run (7 check agents) has 6 skeptics, and every finding left over is listed as unverified and counted as open. The caps are in the script; a caller can lower them and never raise them. The runtime has no clock, so the wall-clock limit belongs to whoever launches the run, for example `timeout 1800 claude -p ...`.

## Gotchas

- **A GO covers files and records, never the robot.** Nobody measured the bus, the link or the clocks. A clean sync table means the configuration agrees on paper. The sheet says so under what was not checked; repeat it when you hand over a GO.
- **The skeptic's default leans toward closing findings.** It returns `real=false` when it cannot confirm, which is right for an audit and the wrong direction for a gate, because a wrongly refuted high finding becomes a false GO. The script therefore holds every refuted high finding as `review`, and the sheet lists all refuted and record-closed rows under the verdict. Read them before you set `reviewedClosures: true`.
- **`closed-by-record` rows that no skeptic checked are the agent's word.** Findings an agent marks as already recorded go straight to that status with the record it cited. Open the cited line for any high one; an open question is not a closing record. The script also holds these high rows as `review` until `reviewedClosures: true`.
- **The hash check is only as wide as the hashes you took.** A file an agent read that was not in `hashesBefore` has no baseline, so a change during the run goes unseen. Hash the model copies, host configs and records you listed, and expect the sheet to name the files it read that had no baseline. Those do not block GO, so a change to one of them goes unseen.
- **A confirmed profile is a decision record, so a wrong one poisons every verdict.** The bus map decides what the command gate calls FORBIDDEN. If the profile misses a bus ID the gate treats every standard ID as a motor address, which is the safe failure. Fill gaps by reading the firmware or vendor spec, never by copying another robot's layout.
- **Agent-proposed commands are vetted again, and that costs a call.** Capture lists from the sync auditor and the first-application steps from the gain gate go through the command gate before you see them. A command the gate never saw is shown as NOT VETTED; run none of those.
- **Skipping an agent is a decision the sheet records.** A single host or a single model copy skips that auditor; a change that touches no gain skips the gain gate. If you pass fewer inputs than the change needs, the sheet is clean for the wrong reason.
- **The gain gate checks evidence, not merit.** PASS means a simulation, written criteria, a bounded step and a one-step rollback exist. It does not say the gains are good, and it never proposes values.
- **A prompt is not a fence.** The agents have no shell, but pair a live session with deny rules in the project settings for the commands that move things (`ros2 topic pub`, `cansend`, remote shells), because a later edit to an agent definition can add tools.

Ideas reimplemented here, with no text copied: a profile builder that compiles robot-specific context before debugging starts (https://arxiv.org/abs/2607.13049), file-based stage handoffs gated by a script (https://arxiv.org/abs/2606.08610), file-ownership boundaries and a read-only reviewer role (https://github.com/wshobson/agents/tree/main/plugins/agent-teams, MIT) and a verify stage that escalates by risk (https://github.com/Yeachan-Heo/oh-my-claudecode, MIT).
