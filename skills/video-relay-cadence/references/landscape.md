# Video Relay Cadence Landscape — verified snapshot
**Verified: 2026-10-12.** Entries were confirmed against live sources on this date — re-verify anything before relying on it if this snapshot is more than ~6 months old.

## ROS 2 relays and bridges
- **web_video_server** — HTTP server that turns ROS image topics into browser-viewable streams. The ros2 branch README lists streams as MJPEG, VP8 (WebM), VP9 (WebM), H264 (MP4), PNG and ROS compressed image, plus JPEG/PNG/compressed snapshots. Stream URL parameters are `topic`, `type` (default mjpeg), `width`, `height` (0 = original size), `quality` (default 95, MJPEG and PNG only), `bitrate` (default 100000 bit/s, H264/VP8/VP9), `default_transport` (default raw) and `qos_profile`. The server parameter `publish_rate` defaults to -1.0, which means no republishing. The README makes no frame-rate or latency claims and lists no per-stream output fps parameter. Status: maintained. Source: https://github.com/RobotWebTools/web_video_server
- **foxglove_bridge** — C++ ROS 2 WebSocket bridge built on the Foxglove SDK, positioned as an alternative to rosbridge with ROS 2 `.msg`/`.idl` schema support. Backpressure is explicit: `message_backlog_size` (default 1024) limits buffered outgoing messages per client and the server "drops the oldest data-plane message on overflow", `min_qos_depth`/`max_qos_depth` default to 1 and 25, and `max_data_track_message_size` (default 100 KiB) drops oversized lossy messages. With `remote_access` enabled it transcodes image topics to video (`video_encoder` picks the backend), and `video_transcode_topic_denylist` defaults to `[".*/compressedDepth"]` so depth pixels do not pass through lossy video. Status: maintained. Source: https://github.com/foxglove/foxglove-sdk/tree/main/ros/src/foxglove_bridge
- **image_transport (image_common) and image_transport_plugins** — image_transport is the core library: a plugin architecture for publishing and subscribing to images in raw or compressed form, with a `republish` node that re-publishes images between transports and a `list_transports` tool. The image_common README's distro table lists branches rolling, lyrical, kilted, jazzy, iron and humble. The image_transport_plugins repo (build badges for Humble, Jazzy, Kilted, Lyrical and Rolling) contains compressed_image_transport, compressed_depth_image_transport, theora_image_transport and zstd_image_transport; its README is inconsistent about whether these target images or point clouds, so check each plugin's own docs. Status: maintained. Source: https://github.com/ros-perception/image_common — Source: https://github.com/ros-perception/image_transport_plugins
- **foxglove_compressed_video_transport** — image_transport plugin that encodes frames into Foxglove's `CompressedVideo` message with FFmpeg/libav. Default encoder is `libx264` (CPU, unaccelerated); `h264_nvenc` and `h264_vaapi` are listed as hardware options. The README says `gop_size` "must be set to 1" for Foxglove (default `bit_rate` 8242880 bit/s). The plugin must be installed on both the encoding and the viewing host, and the subscriber side is documented as unsupported and for debugging only. Status: maintained. Source: https://github.com/ros-misc-utilities/foxglove_compressed_video_transport
- **ffmpeg_image_transport** — image_transport plugin that encodes and decodes with FFmpeg/libav, with H.264 and H.265/HEVC examples and hardware encoders such as `h264_nvenc`, `h264_vaapi` and `hevc_nvenc`. Default `gop_size` is 10 and default encoder is `libx264`. The README warns that encoders buffering frames for inter-frame prediction can add "very large lag", and says a smaller `gop_size` (more frequent keyframes) reduces it. Status: maintained. Source: https://github.com/ros-misc-utilities/ffmpeg_image_transport
- **husarion/rosbridge** — Rust ROS 2 to WebSocket bridge image described on Docker Hub as a "drop-in foxglove-bridge replacement" that speaks the rosbridge v2 JSON/CBOR protocol, so roslibjs clients work unchanged. It adds "H.264 video and Opus audio streamed as compact binary frames on negotiated channels" that the browser decodes with WebCodecs. The page names `rmw_cyclonedds_cpp` as default RMW and does not name a ROS 2 distribution. The source repository is given as github.com/husarion/husarion_rosbridge, which was not opened in this run. Status: maintained. Source: https://hub.docker.com/r/husarion/rosbridge
- **ros_camera_server** — GStreamer-based camera server announced on the ROS Discourse on 2026-05-06 by Stefan Fabian. A single YAML config declares all cameras, each with one input and one or more outputs, and outputs can differ in resolution and framerate; supported outputs are ROS 2, RTP, SRT and WebRTC. The post claims lower latency and CPU use than decode-and-re-encode pipelines, but the benchmark numbers are in plot images that were not readable here, so treat the claim as unverified. AGPL-licensed with a separate license offered on request. Status: maintained (new, 2026). Source: https://discourse.openrobotics.org/t/camera-streaming-made-easy-new-release/54562 — Source: https://github.com/StefanFabian/ros_camera_server

## Browser and network transport
- **Foxglove remote access (WebRTC)** — device-side gateway (the Foxglove SDK or Foxglove Bridge) connects out to Foxglove and streams through a Foxglove-managed SFU with STUN/TURN relays, so the robot needs no inbound ports. Raw and compressed image topics are transcoded to a WebRTC video track whose quality adapts to bandwidth on both legs; avif images and already-compressed video are not transcoded, and depth images should be delivered as data instead of through video. Messages travel over lossy data channels by default to minimize latency, and a message above 1300 bytes is split into fragments, so large messages survive loss poorly. The ROS 1 bridge cannot opt topics out of transcoding. Status: hosted service. Source: https://docs.foxglove.dev/docs/visualization/connecting/live/remote-access
- **Foxglove CompressedVideo schema** — the message format that video-over-ROS paths feed to Foxglove: fields `timestamp`, `frame_id`, `data`, `format`, with ROS 2 type `foxglove_msgs/msg/CompressedVideo` and supported formats `h264`, `h265`, `vp9`, `av1`. H.264 must be Annex B with an SPS NAL unit in every IDR message, VP9 messages "should contain exactly one video frame", and B-frames are unsupported because they need lookahead. Hardware limits and patent licensing mean not every codec works everywhere. Status: maintained. Source: https://docs.foxglove.dev/docs/visualization/message-schemas/compressed-video
- **multipart/x-mixed-replace (MJPEG over HTTP)** — the mechanism behind browser MJPEG streams such as web_video_server's `/stream` URL. The HTML Standard (section 17.2) registers the type, requires the `boundary` parameter defined in RFC 2046, and states that subresources can be of any type; it gives no rate or buffering semantics, so frame pacing is whatever the server writes. Mozilla bug 1113465 (still NEW) proposed accepting only JPEG parts in `<img>` and forbidding size changes after the first part, with later frames to be scaled to the first frame's size (comment 13 calls this the current plan, possibly revisited). A commenter in that bug reports live sites using the type for GIF as well. Status: standardized, browser behavior varies. Source: https://html.spec.whatwg.org/multipage/iana.html — Source: https://bugzilla.mozilla.org/show_bug.cgi?id=1113465
- **GStreamer rtspsrc** — source element that connects to an RTSP server (RFC 2326), creates a `stream_%u` pad per SDP stream and behaves as a live source. `latency` ("Amount of ms to buffer") defaults to 2000 ms, so lower it for low-latency viewing. `drop-on-latency` (default false) tells the jitter buffer never to exceed the latency size, and `protocols` defaults to `tcp+udp-mcast+udp` with negotiation order UDP unicast, UDP multicast, then TCP. Status: maintained. Source: https://gstreamer.freedesktop.org/documentation/rtsp/rtspsrc.html?gi-language=c

## Frame-rate conversion theory
- **FFmpeg `fps` and `framerate` filters** — the `fps` filter converts to a constant frame rate "by duplicating or dropping frames as necessary" (default 25, `round` default `near`, `eof_action` default `round`), so the output cadence is uneven whenever the ratio of input to output rate is not an integer. The `framerate` filter instead changes rate "by interpolating new video output frames from the source frames", with `interp_start` 15, `interp_end` 240 and scene-change threshold `scene` 8.2 by default, and it is not designed for interlaced media. Choosing between them is the core drop/duplicate versus blend decision for a relay. Status: maintained. Source: https://ffmpeg.org/ffmpeg-filters.html
- **GStreamer videorate** — takes timestamped frames and outputs a steady stream at the source pad's framerate; per its documentation "The correction is performed by dropping and duplicating frames, no fancy algorithm is used to interpolate frames (yet)". Properties include `drop-only` (no duplicates, default false), `max-rate` and `average-period` (caps rate by dropping frames above a moving-average limit). `drop-only` is the pipeline-level way to avoid repeated frames. Status: maintained. Source: https://gstreamer.freedesktop.org/documentation/videorate/index.html
- **Telecine and 2:3 pulldown (judder)** — Wikipedia's Three-two pull down article describes 24 fps film mapped to video as frame A on two fields, B on three, C on two, D on three, repeating after four film frames. The Telecine article says 2:3 pulldown creates a slight error in the video signal, most apparent in slow, steady camera movements, which look slightly jerky (telecine judder). The Motion interpolation article adds that repeating each frame a whole number of times (24 fps content on a 120 Hz display, each frame shown five times) avoids pulldown judder without interpolation, and that interpolation is only needed for rates not evenly divisible. Applied to a relay, a camera at 15 fps shown at 60 Hz is even (4 refreshes per frame) but 20 fps at 30 Hz is not (1.5 refreshes per frame, so holds alternate between 1 and 2). Status: reference. Source: https://en.wikipedia.org/wiki/Three-two_pull_down — Source: https://en.wikipedia.org/wiki/Telecine — Source: https://en.wikipedia.org/wiki/Motion_interpolation

## Measurement tools
- **ros2 topic hz** — reports average rate (inverse of the mean interval), min and max interval, standard deviation and window size over a sliding window (`--window`, default 10000 messages; `--filter` for a Python expression; `--wall-time` when the clock is not published). The help text warns the result "may not exactly match the publisher's rate" because it measures arrival at its own subscription. Std dev and max interval are the numbers that expose uneven cadence; the average alone hides it. Status: maintained. Source: https://github.com/ros2/ros2cli/blob/rolling/ros2topic/ros2topic/verb/hz.py
- **HTMLVideoElement.requestVideoFrameCallback** — browser API whose callback metadata includes `presentationTime`, `expectedDisplayTime`, `presentedFrames` (a jump greater than one between callbacks shows frames missed) and `mediaTime`; for WebRTC sources, `captureTime`, `receiveTime` and `rtpTimestamp` may also be present. Differencing consecutive `presentationTime` values gives the cadence a viewer actually sees, which is the number that matters for judder. MDN says the WebRTC fields "may be available", so check for them. Status: maintained. Source: https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback
- **WebRTC statistics (RTCInboundRtpStreamStats)** — W3C spec fields for receiver-side cadence: `framesPerSecond` ("The number of decoded frames in the last second"), `freezeCount` (total video freezes, defined against the gap between rendered frames and the average of the last 30), `totalInterFrameDelay` and `totalSquaredInterFrameDelay` (sums for computing inter-frame delay variance, paired with `framesRendered`), plus `framesDropped` and `jitterBufferDelay`. Variance of inter-frame delay is the WebRTC-side analogue of std dev in `ros2 topic hz`. Status: standard. Source: https://www.w3.org/TR/webrtc-stats/
