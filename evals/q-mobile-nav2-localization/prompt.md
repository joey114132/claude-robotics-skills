expected_outcome: "The question is framed as AMCL parameter tuning, but the root cause is that odom->base_link is a static identity transform. Nav2 requires odom => base_link to be a live, continuous motion estimate (wheel encoders, IMU, lidar or visual odometry, typically fused with robot_localization) plus a nav_msgs/Odometry message for velocity; AMCL only publishes map => odom as a slow correction on top of it (REP 105: odom is continuous, map jumps; the AMCL alpha1-5 values are documented as the expected noise of the odometry estimate, so they presuppose that odometry exists). With an identity transform AMCL's motion model sees zero motion, so its filter updates (gated by update_min_d and update_min_a) are not triggered by real movement and the predicted pose has no motion input, while the local costmap and controller in the odom frame see a robot that never moves and get no velocity feedback. An expert answer must say the AMCL parameters (alpha1-5, update_min_d, laser_likelihood_max_dist) are not the fix, and recommend supplying a real continuous odom->base_link, for example by adding encoders or by lidar scan-matching odometry and an IMU fused in robot_localization or an equivalent EKF, and only then tuning AMCL. I'm bringing up Nav2 with AMCL on a differential-drive cart with a 2D lidar. The hub motors have no encoders, so my bringup just publishes a static odom->base_link transform to keep the TF tree complete, and I let AMCL do all the localization against the saved map. In RViz the estimated pose doesn't follow the cart smoothly, and the cart weaves back and forth along the planned path. Which AMCL parameters should I tune (the alpha noise values, update_min_d, laser_likelihood_max_dist) to make it settle?
